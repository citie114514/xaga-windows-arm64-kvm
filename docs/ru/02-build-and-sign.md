# Сборка и подпись — пошаговое объяснение

[中文](../02-build-and-sign.md) | [English](../en/02-build-and-sign.md) | [日本語](../ja/02-build-and-sign.md) | **Русский**

На этой странице: **что именно меняет патч NoGZ**, **как собрать**, **как подписать** и **как проверить**.

> Инструмент — [`mtk-mod-tee-nogz`](https://github.com/MT6895-Mainline/mtk-mod-tee-nogz) (апстрим).
> Скрипт в один клик в этом проекте лишь связывает его с «записью + проверкой».
> Апстрим прямо заявляет: **в нём нет прошивок, нет образов для прошивки, а его скрипты ничего не
> прошивают** — эту половину добавляет наш проект.

## 1. Что именно меняет патч

Он меняет **логику передачи управления у члена `atf`** внутри `tee.img`. Целевое состояние:

> **Сохранить вход LK в EL1h и передачу ядру AArch64 в EL2h**, а также **синхронизировать тег
> GZ-info, общий для ATF и LK**.

Апстрим оставляет три вида «неправильных подходов» как контрпримеры (поэтому не стоит патчить это
самостоятельно наугад):

| # | Контрпример | Пояснение |
|---|---|---|
| 1 | `D2A21E08` на самом деле грузит `0x10f00000`, а не `0x50f00000` из LK | Правильная кодировка — **`D2AA1E08`** |
| 2 | Оригинальный путь входа LK в EL2 **обращается к `CPTR_EL3`** | Поэтому **нельзя** принудительно перевести и LK, и ядро на уровень EL2h |
| 3 | Изменение только GZ getter в ATF **не меняет автоматически** состояние LK | Нужно **синхронизировать общий тег**, иначе позже всё равно будет выбран путь GZ unmap |

**Главное**: патч **сохраняет резервирование и переотображение памяти GZ** и **не утверждает, что
возвращает эту память** — он лишь делает EL2 доступным для Linux (и тем самым открывает `/dev/kvm`).

## 2. Подготовка окружения

**Python 3.10+**, желательно в отдельном виртуальном окружении.

Linux / macOS:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Зависимости — **Capstone** (дизассемблер) и **Unicorn** (эмуляция выполнения); обе нужны для офлайн-анализа
и не требуют ни устройства, ни сети.

**Также понадобится** (не поставляется с репозиторием, готовьте сами):

- Полный каталог инструмента **`pwnage24mtk`** (с `sign_mtk_cert.py` / `verify_mtk_image.py`)
- **Прошивка, соответствующая устройству**: `tee.img` / `lk.img` / `preloader.bin`
  → надёжнее всего снять прямо с устройства (см. раздел 3 в [01-enable-kvm.md](01-enable-kvm.md))

## 3. Сопоставление модели (этот этап нужно пройти первым)

Инструмент сопоставляет пары TEE/LK по **полной SHA-256**, а **не** по названию модели или размеру файла:

| Profile | Целевой образец |
|---|---|
| `xaga` | Redmi Note 11T Pro / Pro+ (MT6895) **← устройство, на котором измерял этот проект** |
| `peral` | Xiaomi 13T |
| `yunluo` | Уже проанализированная пара TEE/LK для yunluo |

> **Одинаковое название модели, близкая версия прошивки, совпадающие размеры файлов — ничто из этого
> не заменяет совпадение хешей.** Поэтому всегда **снимайте данные с самого устройства**; не ищите
> в интернете пакет прошивки «для такой же модели».

Полные хеши и определения адресов лежат в `references/profiles.json` репозитория инструмента.

```bash
# Посчитайте хеш снятого образа и сравните с profiles.json
sha256sum dump/tee_a.img dump/lk_a.img
```

## 4. Шаг первый: только офлайн-проверка (без подписи и без результата)

Сначала запустите `--check-only`, чтобы убедиться, что пара TEE/LK совпадает и регрессии патча проходят:

Linux / macOS:

```bash
.venv/bin/python scripts/build.py \
  --profile xaga \
  --tee    "$HOME/private-firmware/xaga/tee.img" \
  --lk     "$HOME/private-firmware/xaga/lk.img" \
  --check-only
```

Windows:

```powershell
$inputDir = Join-Path $HOME 'private-firmware\xaga'
.\.venv\Scripts\python.exe scripts/build.py --profile xaga `
  --tee "$inputDir\tee.img" --lk "$inputDir\lk.img" --check-only
```

Что делает `--check-only`:

- ✅ Запускает офлайн-регрессию патча TEE/LK (PC/SPSR, реальные парсеры тегов ATF/LK, общие флаги, шлюз GZ и намеренно построенные контрпримеры)
- ❌ **Не** определяет режим подписи, **не** создаёт образ, **не** вызывает pwnage

**Что покрывает офлайн-регрессия** (в нашем отчёте — **14/14 пройдено**):

| Проверка | Результат |
|---|---|
| Состояние PC / SPSR | ✓ |
| Парсер тегов ATF | ✓ |
| Парсер тегов LK | ✓ |
| Общие флаги | ✓ |
| Шлюз GZ | ✓ |
| Намеренно построенные контрпримеры (должны быть отклонены) | ✓ |

> ⚠️ «14 записей» в отчёте — это **ограниченные записи проверок, а не 14 полных тестов загрузки устройства**.
> Офлайн-`VALID` ≠ устройство обязательно загрузится.

## 5. Шаг второй: определить режим подписи preloader

Способ подписи **зависит от режима обхода сертификатов в preloader**, поэтому сначала проверьте его
встроенным в инструмент детектором:

```bash
.venv/bin/python scripts/detect_pl_cert_mode.py \
  "$HOME/private-firmware/xaga/preloader.bin" --json
```

По умолчанию полные доказательства (включая дизассемблер) записываются в новый файл в каталоге `logs/`,
который исключён из git.

| Результат детектора | Соответствующий аргумент pwnage |
|---|---|
| **`new`: `NEW_PARSER`** | **Не добавлять аргумент режима** (ни `--legacy`, ни `--new`) |
| **`legacy`: `LEGACY`** | **Добавить `--legacy`** |
| `NEED_MANUAL` / не поддерживается / неоднозначно | **Остановиться и разбирать руками**; не угадывать по модели |

> На этом устройстве (Redmi Note 11T Pro+) измерено **`LEGACY`**, поэтому применяется `--legacy`.
>
> Обратите внимание: «new ничего не добавляет» означает **отсутствие дополнительной опции режима**, а не
> пропуск входных файлов и опций записи. Обычные `--all -w -o` всё равно нужны.
>
> Детектор — это **анализ статических доказательств**; он не равен состоянию efuse, эксплуатируемости
> уязвимости или проверке загрузки на устройстве.

## 6. Шаг третий: собрать подписанную копию

```bash
.venv/bin/python scripts/build.py \
  --profile xaga \
  --tee       "$HOME/private-firmware/xaga/tee.img" \
  --lk        "$HOME/private-firmware/xaga/lk.img" \
  --preloader "$HOME/private-firmware/xaga/preloader.bin" \
  --tools     ../pwnage24mtk \
  --out-dir   outputs/xaga-run-01
```

**На что обратить внимание**:

- `--preloader` обязателен (режим подписи привязан к нему); скрипт сам вызывает детектор, так что
  **выбирать режим вручную не нужно**
- Хеш preloader записывается в manifest, но **скрипт не может по имени файла доказать, что он совпадает
  с тем, что реально использует устройство**
- `--out-dir` **обязан быть новым, несуществующим каталогом** — для повторного прогона берите новый,
  **не перезаписывайте старые результаты** и тем более **не подавайте подписанный артефакт обратно на вход**

### Структура результатов

```text
outputs/xaga-run-01/
  cert-mode.txt          # полные доказательства детектора
  detect.log             # JSON-вывод детектора или ошибка
  tee.unsigned.img       # промежуточный файл (НЕ подписанный результат!)
  tee_nogz_legacy.img    # в режиме LEGACY -> это результат
  # tee_nogz_new.img     # в режиме NEW_PARSER результат этот
  sign.log
  verify.log
  disassembly.txt
  manifest.json
```

**Судить об успехе по одному наличию `.img` нельзя** — смотрите **код возврата, полные логи и manifest.json**.

## 7. Шаг четвёртый: проверка подписи (нужно два VALID)

```bash
cd ../pwnage24mtk
python verify_mtk_image.py --all ../outputs/xaga-run-01/tee_nogz_legacy.img
```

**Вы должны увидеть два `Result: VALID`** (группа ATF и группа TEE):

```
Result: VALID
Result: VALID
```

Измерено здесь:

| Проверка | Результат |
|---|---|
| `verify_mtk_image.py --all` | **2 × `Result: VALID`** ✓ |
| Подпись CERT1 / CERT2 | OK ✓ |
| Хеш заголовка / хеш данных образа | OK ✓ |
| Был ли изменён член `tee` | **не изменён** ✓ |
| ATF против повторного патча | **побайтово идентично** ✓ |
| Официальная регрессия из 14 пунктов | **14/14 пройдено** ✓ |

**Непроверенный пункт (честно указан)**: `Trusted root check: skipped`
→ Сравнение этой цепочки сертификатов с корнем доверия в eFuse устройства **невозможно проверить офлайн**;
доказывает только реальная загрузка.

> Здесь используется **обработка сертификатов сторонним инструментом**. Это не означает владения закрытым
> ключом производителя и не даёт нового официального разрешения. Механизм — дефект разбора ASN.1-сертификатов
> у MTK (тот же класс, что CVE-2023-20696; исправлен только в CVE-2025-20730).

## 8. Шаг пятый: «на 1072 байта больше раздела»

Это была **самая большая ловушка этого проекта**, и её обязательно нужно обработать:

```
без подписи : 5 242 880   (= размер раздела tee, заполняет ровно)
с подписью  : 5 243 952   (+1072)
```

Прирост даёт **обёртка BIT STRING (987 B)** плюс **CERT2 dsize 982→2059 (выровнено до 2064)**.

**Но точка вставки находится после `atf`, поэтому хвостовое нулевое заполнение полностью не изменилось:**

| Член | без подписи | с подписью |
|---|---|---|
| `atf` | 0x200 | 0x200 (**не изменился**) |
| `tee` | 0x46440 | 0x46870 (+1072) |
| `cert1` | 0x353a40 | 0x353e70 (+1072) |
| `cert2` | 0x354310 | 0x354740 (+1072) |
| **хвостовое нулевое заполнение** | 1 751 322 | **1 751 322 (не изменилось)** |

В хвосте **1.75 MB нулей** → **обрезав 1072 байта нулевого заполнения, получаем ровно 5 MiB без потери
реальных данных**.

```bash
# Сначала побайтово убедитесь, что превышение состоит только из 0x00
python - <<'PY'
data = open('tee_nogz_legacy.img','rb').read()
tail = data[5242880:]
print('байт превышения:', len(tail), ' ненулевых байт:', sum(1 for b in tail if b))
PY

# Только убедившись, что всё нули, обрезайте
head -c 5242880 tee_nogz_legacy.img > tee_nogz_flash.img
sha256sum tee_nogz_flash.img
```

**Если в превышении есть ненулевые байты → остановитесь и разбирайтесь руками, не обрезайте силой.**

Скрипт в один клик делает это автоматически и **настаивает на проверке «всё нули» перед обрезкой**.

## 10. Хотите адаптировать это под другую модель MTK?

Требование апстрима: **новая версия должна предоставить полную пару SHA-256**; см. `references/adaptation.md`.

> **Не обходите проверку версии, правя существующие хеши или удаляя проверки.**

Примерный процесс:

1. Снять `tee` / `lk` / `preloader` с целевого устройства
2. Посчитать SHA-256 и сравнить с проанализированными образцами в `references/profiles.json`
3. Если совпадений нет → нужно **добавить новый profile** по `references/adaptation.md` (это означает
   понимание смещений и инструкций ATF/LK)
4. Прогнать регрессию `--check-only` → затем идти по процессу подписи

**Та же модель на другой версии прошивки тоже может не совпасть** — это инструмент уровня «точного
образца прошивки», места для нечёткого сопоставления здесь нет.

## 11. Границы проверки (обязательно к прочтению)

Границы, которые апстрим явно перечисляет, приведены дословно (важно — не переинтерпретируйте):

- Регрессия известных образов проверяет PC/SPSR, реальные парсеры тегов ATF/LK, общие флаги, шлюз GZ и намеренно построенные контрпримеры.
- 14 записей в отчёте — это **ограниченные записи проверок, а не 14 полных тестов загрузки устройства**.
- Возможности CPU, CurrentEL, часть системных регистров и обслуживание кэша **явно смоделированы**;
  полная инициализация LK, Linux, реальный ERET, PSCI и периферия **не выполняются**.
- Если офлайн-проверка подписи сообщает `Trusted root check: skipped`, **корень доверия устройства остаётся непроверенным**.
- CI не содержит реальных прошивок и **не может заменить** регрессию известных образов из `build.py --check-only`,
  тем более **не может доказать совместимость с железом**.

**При отчёте указывайте раздельно**: идентичность входных данных, офлайн-результаты, фактическую
обратную связь от устройства и непроверенные пункты.

## 12. Известный баг апстрим-инструмента (мы отправили PR)

`scripts/build.py:340` вызывает `sign_all_flag(args.tools)`, но **эта функция нигде в файле не определена**
→ путь подписи гарантированно даёт `NameError`. `--check-only` завершается раньше и поэтому это не всплывало.

(Кроме того, у самого `sign_mtk_cert.py` нет аргумента `--all`, поэтому эта функция должна просто возвращать `[]`.)

Исправление — в [issues/tee-nogz-1-sign-all-flag.md](../../issues/tee-nogz-1-sign-all-flag.md).
