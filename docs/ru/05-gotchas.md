## 1. 🔴 ESP пустой — прошивка не находит загрузочное устройство

**Симптом**
```
BdsDxe: No bootable option or device was found.
```
Либо зависание на экране UEFI / падение прямо в UEFI Shell.

**Причина**
При развёртывании образа инструментами вроде Dism++ **загрузочные файлы в ESP не записываются**.
В только что отформатированном ESP есть лишь это:

```
EFI\Boot\BOOTAA64.EFI                     MISSING
EFI\Microsoft\Boot\bootmgfw.efi           MISSING
EFI\Microsoft\Boot\BCD                    MISSING
```

**Решение**
```powershell
bcdboot G:\Windows /s S: /f UEFI /v
```
x64-версия `bcdboot` **умеет** записывать загрузчик для ARM64-образа и сама выбирает
`bootaa64.efi`. После этого проверьте, что PE machine у `bootmgfw.efi` равен **`0xAA64`**.

Подробности — в [03-windows-vm.md](03-windows-vm.md), раздел 2.3.

## 2. 🔴 Порт VNC не тот, о котором вы думаете

**Симптом**
После `adb forward tcp:5900 tcp:5900` VNC-клиент не подключается — или подключается к чёрному
экрану. Но **иногда работает**, так что поведение выглядит хаотичным.

**Причина (два слоя)**

1. В `-vnc 127.0.0.1:N` **`N` — это номер display, а не порт**; порт = `5900 + N`
   → `-vnc 127.0.0.1:5900` на самом деле слушает **11800** ✗ (не 5900)
2. **Если порт занят, QEMU не выдаёт ошибку** — он **молча увеличивает номер display**
   → вы думаете, что он на 5900, а он на **5901** ✗

**Решение**

```bash
# Правильная форма: :0 -> порт 5900
-vnc 127.0.0.1:0,lossy=on
```

**И** дождитесь, пока порт действительно освободится, а после запуска проверьте фактический порт:

```bash
# Перед запуском
for i in $(seq 1 30); do
    netstat -tln | grep -q ":5900 " || break
    sleep 1
done

# После запуска
netstat -tlnp | grep qemu        # должно быть 127.0.0.1:5900
```

`scripts/phone/boot-win.sh` уже делает и то, и другое, и **завершается сразу, если проверка
не прошла**.

## 3. 🔴 `-cpu host` случайно падает на big.LITTLE

**Симптом**
```
qemu-system-aarch64: Failed to put registers after init: Invalid argument
```
Одна и та же команда, запущенная 5 раз, иногда срабатывает, а иногда нет.

**Причина**
`-cpu host` перечисляет возможности **того CPU, на котором случайно оказался QEMU**. MTK —
это 4×A78 + 4×A55, поэтому если планировщик мигрирует процесс между A55 и A78 во время записи
регистров vCPU → `EINVAL`.

**Измеренные данные**

| Условие | Доля успеха |
|---|---|
| Без привязки | **2/5** ✗ |
| `taskset 1` (cpu0, A55) | **3/3** ✓ |
| `taskset 80` (cpu7, A78) | **3/3** ✓ |
| `taskset f0` (cpu4-7, кластер A78) | **3/3** ✓ |

**Решение**
```bash
taskset f0 qemu-system-aarch64 ...
```

> Разные варианты `-cpu` (`host,pmu=off`, `host,sve=off`, …) ведут себя **непредсказуемо —
> случайность доминирует над любыми различиями в возможностях**. Не пытайтесь обойти это
> подкручиванием возможностей — **просто зафиксируйте привязку к ядрам**.

## 4. 🔴 `pkill -f` убил собственную оболочку

**Симптом**
Скрипт обрывается на середине без вывода, и процесс не остаётся запущенным.

**Причина**
```bash
adb shell su -c 'pkill -f qemu-system-aarch64.real; ...'
```
`pkill -f` сопоставляет **всю командную строку**, а **в командной строке внешнего `su -c` эта
строка присутствует** → **он убивает и собственную оболочку**.

**Решение**
Сопоставляйте по **короткому имени процесса** (`pkill` по умолчанию смотрит только имя процесса):

```bash
pkill qemu-system-aar
```

Либо поместите `pkill` внутрь **файла скрипта** (в его собственной командной строке этой строки нет):

```bash
# scripts/phone/stop-vm.sh
pkill qemu-system-aar
```

## 5. 🟠 `-device usb-tablet,bus=usb` сообщает об отсутствии шины

**Симптом**
```
qemu-system-aarch64: -device usb-tablet,bus=usb: Bus 'usb' not found
```
QEMU вообще не запускается.

**Причина**
В `-device qemu-xhci,id=usb` значение `id=usb` — это **просто id устройства**; шина USB
называется **`usb.0`** (`<id>.0`).

**Решение**
**Уберите `bus=`** и дайте устройству автоматически подключиться к единственному USB-контроллеру
(самый простой путь):

```bash
-device qemu-xhci,id=xhci -device usb-tablet -device usb-kbd
```

## 6. 🟠 Подключение установочного ISO Windows перехватывает загрузку

**Симптом**
Система установлена, но при загрузке попадаешь в установщик Windows.

**Причина**
Установочный ISO Windows **загрузочный** (El Torito + `EFI\BOOT\BOOTAA64.EFI`), поэтому UEFI
может предпочесть его.

**Решение**
- После установки **не подключайте** установочный ISO Windows
- Если нужен привод, подключайте **`virtio-win.iso`** — это **чисто дисковый образ данных**
  (ISO9660 от `genisoimage`: без El Torito и без каталога EFI), поэтому **подключать безопасно**

## 7. 🟠 `adb push` в `/data/media/0/` — отказ в доступе

**Симптом**
```
adb: error: stat failed when trying to push to /data/media/0/DroidVM/win.vhdx: Permission denied
```

**Причина**
`/data/media/0` — каталог, доступный только root; пользователь `shell`, под которым работает adb,
туда писать не может.

**Решение**
Сначала скопируйте туда, куда `shell` может писать, затем переместите под root
(**переименование внутри одной файловой системы мгновенно**):

```bash
adb push win.vhdx /data/local/tmp/win.vhdx
adb shell su -c 'mv /data/local/tmp/win.vhdx /data/media/0/DroidVM/'
```

> Кстати: `/storage/emulated/0/...` — это **монтирование FUSE**, а `/data/media/0/...` — **нативный
> путь** к тому же файлу. Используя нативный путь, QEMU обходит слой FUSE.
> (Измеренная скорость чтения примерно одинакова, ~950 MB/s, но нативный путь стабильнее.)

## 8. 🟠 Время внутри ВМ становится 2768 годом

**Симптом**
Панель задач Windows показывает `2768/12/24`.

**Причина**
Начальное значение RTC на стороне QEMU читается с отклонением (**+742 года**).
Но **PL031 RTC — это 32-битный счётчик секунд, физически не способный выйти за 2106 год** —
значит, **это значение не может исходить от RTC**; это баг преобразования в сборке QEMU.

**Решение**
**Как только появляется сеть, Windows NTP исправляет это автоматически** (что заодно доказывает
работоспособность сети). Вручную:

```powershell
# Внутри Windows, PowerShell от администратора
Stop-Service w32time; Set-Service w32time -StartupType Disabled
Set-Date -Date "2026-10-06 03:20:00"
```

Либо правый клик по часам в панели задач → настройка даты и времени → отключить «Устанавливать
время автоматически» → задать вручную.

## 9. 🟠 Система конфигурации DroidVM: три вещи, которые нужно различать

Приложение DroidVM и командная строка QEMU — это **два взаимно несовместимых способа запуска ВМ**.
Смешивать их — гарантированно наступить на грабли.

### (a) Конфиги, создаваемые приложением, **сами по себе не работают**

Аргументы запуска, которые генерирует DroidVM, неполны:

- **У virtio-сетевой карты нет бэкенда `-netdev`** → в госте нет сети
- **Нет `virtio-balloon`** → память только растёт

**Решение**: поставить **скрипт-обёртку**, чтобы `qemu-system-aarch64`, который вызывает приложение,
перенаправлял вызов настоящему `.real` и дополнял недостающее — полная инструкция в
[scripts/phone/README.md](../../scripts/phone/README.md).
Он **дополняет только то, чего не задал вызывающий**, поэтому вашим собственным скриптам запуска
он не мешает.

### (b) Порт VNC по умолчанию **случайный**

`screens.*.vnc.port` в `vms.json` по умолчанию **`-1`** = «выбрать автоматически»:

```json
"vnc": { "host": "127.0.0.1", "port": -1, "password": "", "password_auth": false }
```

**Следствие**: порт может отличаться при каждом запуске ✗ — то, что вы пробросили через
`adb forward tcp:5900`, никто не слушает ✗. Частая причина «ВМ явно работает, а VNC не
подключается».

Этот проект **обходит этот путь**: `boot-win.sh` жёстко прописывает `-vnc 127.0.0.1:0` (= 5900)
и после запуска перепроверяет фактический порт.

> Задать поле `port` фиксированным значением — **теоретически другой путь, но непроверенный**,
> к тому же он несёт риск из пункта (c) ниже, поэтому скрипты проекта на него не полагаются.

### (c) Правка `vms.json` вручную ломает чтение в приложении

**Симптом**
Вы правите `vms.json` руками (например, меняете путь к диску), и ВМ **исчезает** из приложения
с сообщением «текущая версия не может это прочитать».

**Причина**
DroidVM проверяет по собственной строгой схеме и **не знает добавленных вручную полей**, поэтому
выбрасывает запись целиком.

**Решение**
- **Меняйте только уже существующие поля** (например `disks[].path`, `screens.*.exporter`) — **никогда не добавляйте новые**
- Сохраняйте исходного владельца и права:
  ```bash
  OWN=$(stat -c %u vms.json); GRP=$(stat -c %g vms.json); MODE=$(stat -c %a vms.json)
  # ... правка ...
  chown $OWN:$GRP vms.json; chmod $MODE vms.json
  ```
- **Сначала сделайте копию**: `cp vms.json vms.json.bak`

### Вывод: выберите один способ, не смешивайте

| Путь | Плюсы | Минусы |
|---|---|---|
| **Командная строка `boot-win.sh`** (рекомендуется) | Полный контроль над аргументами, порт жёстко 5900, не зависит от приложения | Нет графического интерфейса; менять аргументы — править скрипт |
| **Запуск из приложения DroidVM** | Есть интерфейс, можно вести несколько ВМ | Аргументы неполны (нужна обёртка), порт случайный, конфиг нельзя править руками |

> **Не используйте оба одновременно**: запуск из приложения переписывает `vms.json`, а запуск из
> командной строки его вообще не трогает.

## 10. 🟡 `virtio-gpu-rutabaga-pci` мгновенно падает

**Симптом**
```
exit=139      # SIGSEGV
```
QEMU умирает моментально, без вывода.

**Причина**
`virtio-gpu-rutabaga-pci` (путь gfxstream) вместе с `-display egl-headless` вызывает segfault на
этой сборке. Кстати, `virtio-gpu-gl-pci` с `-display none` тоже выдаёт
`The display backend does not have OpenGL support enabled`.

**Решение**
- Для обычного вывода используйте **`virtio-gpu-pci`** (Windows использует `viogpudo`)
- Для **virgl** (имеет смысл только с гостем Linux) — **`virtio-gpu-gl-pci` + `-display egl-headless`** (проверено: инициализируется успешно)
- **Не используйте rutabaga**

## 11. 🔴 **Патч перестаёт работать после записи ROM / OTA**

**Симптом**
После прошивки нового ROM `/dev/kvm` исчезает — либо вы записали в `tee_a` патч, **собранный из
другой прошивки**, и это **выглядит как зависание при загрузке** (⚠️ но сначала прочитайте пункт 12 —
первая загрузка после записи патча и так висит на втором экране около 2 минут ✗).

**Причина**
Патч NoGZ изменяет логику передачи управления у члена `atf` внутри раздела `tee`, поэтому
**патч действителен только для той базы `tee`, из которой он собран**.

Измерено (тот же Redmi Note 11T Pro+, два устройства):

| Устройство | `tee_a` | `lk_a` | Результат |
|---|---|---|---|
| Устройство 1 · штатный Android 15 | `f8f286f1…` → записан патч `f1511dca…` | `8cbaa2e8…` | ✅ загружается + KVM |
| Устройство 1 · обновление до **Android 16** | патч `f1511dca…` (**не менялся**) | **`a17d87c6…` (изменился!)** | ✅ **по-прежнему загружается + KVM** |
| Устройство 2 · та же модель, тот же ROM | обновлён ROM'ом до `a91f5ded…` | `a17d87c6…` | запись патча от устройства 1 → выглядело как зависание ⚠️ |

**Вывод (контринтуитивный, но измеренный)**:

- ✅ **Изменение `lk` не влияет на патч** (у устройства 1 `lk_a` заменили — всё работает)
- ✅ **Изменение `gz` / `dtbo` / `boot` / `system` тоже не влияет** (пережило Android 15 → 16)
- ❌ **Изменение базы `tee` ломает патч** — единственное известное «слабое место»
- ⚠️ **Одна партия прошивки даёт одну базу**, разные партии могут отличаться (база `bd4b13a7…` из
  апстримного профиля `xaga` — третья партия в этой истории); это **не** «у каждого устройства своя»

> 🛠 **Важное исправление (2026-10-06)**: «зависание» в последней строке **опиралось на
> ненадёжные данные**. Позже выяснилось, что **первая загрузка после записи патча в норме висит на
> втором экране почти 2 минуты** (см. пункт 12). Тогда мы не дождались и объявили устройство
> кирпичом ✗.
> Поэтому на вопрос «работает ли патч от другой базы» сейчас следует отвечать **«не проверено»** ⚠️,
> а не «обязательно сломается» ✗. Рекомендация использовать патч под свою базу остаётся верной ✓,
> но причина — **совпадение версии TEE OS**, а не то, что иначе будет зависание.

**Самое неприятное: пакет ROM без образа `tee` всё равно может его изменить**

В ROM, записанном на устройство 2, **не было образа `tee` вообще**, но после записи `tee_a`
изменился с `f8f286f1…` на `a91f5ded…` (вероятно, из-за обновления прошивки при первой загрузке
или из-за `super.img`).
**Значит, нельзя судить об изменении по наличию `tee` в пакете.**

**Решение**

```bash
# 1) Перед записью ROM сделайте бэкап
adb shell su -c 'dd if=/dev/block/by-name/tee_a of=/data/local/tmp/tee_a.bak bs=4096'

# 2) После записи посчитайте хеш и сравните с "совместимой базой" патча
adb shell su -c 'dd if=/dev/block/by-name/tee_a bs=4096 2>/dev/null | sha256sum'
```

| Результат | Следующий шаг |
|---|---|
| Не изменился | ✅ патч продолжает работать, ничего делать не нужно |
| Изменился | ❌ патч недействителен → **снять новые `tee_a`/`lk_a`/`preloader_raw_a` и пересобрать** (готовый образ из другого ROM не подойдёт) |

**Самый простой способ проверить, сменилась ли база** — посмотреть на нетронутый слот:

```bash
adb shell su -c 'dd if=/dev/block/by-name/tee_b bs=4096 2>/dev/null | sha256sum'
# = f8f286f1… -> база не менялась ✓
```

**Откат**: запишите обратно сохранённый `tee_a`; либо переключитесь на слот B
(`tee_b` никогда не изменялся — естественная страховка).

## 12. 🔴 **Первая загрузка после записи патча висит на втором экране около 2 минут — это не кирпич!**

**Симптом**
После записи патча NoGZ и перезагрузки телефон стоит на **втором экране загрузки** (logo2 /
крутилка) и **1–2 минуты ничего не происходит** ✗ — выглядит ровно как кирпич.

**Но это нормально** ✓ — измерено (устройство 2, после записи `17ec8497…` в `tee_a` и перезагрузки):

```
 20s   adb уже видит устройство, но sys.boot_completed=0
 30s   ...
 140s  всё ещё ждём (целых 120 секунд на экране ничего не менялось)
 150s  sys.boot_completed=1   <- оно поднялось само ✓
```

**Результат**: `/dev/kvm` нормально появился ✓, система цела ✓, ни один из 497 пакетов приложений
не потерян ✓

**Причина (предположение)**
С патчем ATF больше не передаёт EL2 в GZ, поэтому какое-то звено цепочки загрузки **ждёт ответа от
GZ**, не дожидается, срабатывает таймаут — и загрузка идёт дальше. То есть «висит, но не мертво».

### ✅ Правильное поведение: **подождать 3 минуты**

- **Не** считайте это кирпичом ✗
- **Ни в коем случае** не торопитесь нажимать «Громкость вниз + Питание» для входа в fastboot ✗ —
  **это прервёт загрузку** ✗ и превратит загрузку, которая бы завершилась успешно, в реально
  незагружающееся устройство ✗
- Только если **более 5 минут** вообще нет изменений, стоит подозревать патч от чужой базы ✗

**После первой загрузки последующие проходят нормально** ✓ (того таймаута рукопожатия больше нет).

### Как отличить «нормальную медленность» от «настоящей поломки»

| Признак | Нормально ✓ | Настоящая поломка ✗ |
|---|---|---|
| Экран | висит на **втором** экране (logo2) с крутилкой | висит на **первом** экране, либо после чёрного экрана **сам уходит в fastboot** |
| adb | **устройство видно** (`adb devices` показывает серийник) | не видно, либо уже режим fastboot |
| Время | поднимается само за 1–3 минуты | более 5 минут без изменений |
| Действие | **ждать** ✓ | восстановить бэкап (см. раздел отката в [tee/README.md](../../tee/README.ru.md)) |

> 💡 Урок: этот проект однажды зря потратил восстановление, потому что не дождался и принял это
> за настоящий кирпич. **После записи патча дайте первой загрузке 3 минуты.**

## Приложение: то, что выглядит как грабли, но ими не является

| Симптом | Правда |
|---|---|
| `warning: nic virtio-net-pci.0 has no peer` | У сетевой карты нет бэкенда (нет `-netdev user,id=n0`). Это лишь предупреждение, **но сеть работать не будет** |
| AAVMF молчит десятки секунд перед стартом | Встроенная запись по умолчанию `Boot0002 "UEFI Misc Device"` сначала выжидает таймаут; это нормально |
| Экран на миг чернеет при первой загрузке | Windows перезагружается / меняет режим вывода. **Просто переподключите VNC**; прогресс не теряется (он на диске) |
| `Trusted root check: skipped` | Офлайн-проверка подписи пропускает сравнение с корнем доверия — **доказать может только реальная загрузка** (это не ошибка) |
| `/dev/kvm` отвечает `Invalid argument` | Это **нормально**! Значит `open()` уже прошёл SELinux (Enforcing) и просто не получил аргументов |
| QEMU не находит `libbinder_ndk.so` | QEMU из DroidVM нужен `export LD_LIBRARY_PATH=/system/lib64` |

## Рекомендуемый порядок диагностики

Когда «не загружается», проверяйте в этом порядке:

```
1. adb shell su -c 'ls -l /dev/kvm'                    <- есть ли KVM (предусловие)
2. adb shell su -c 'cat /data/local/tmp/boot.out'      <- вывод скрипта запуска (включая проверку порта)
3. adb shell su -c 'cat /data/local/tmp/win-qemu.log'  <- собственные ошибки QEMU
4. adb shell su -c 'cat /data/local/tmp/win-serial.log'<- вывод последовательного порта прошивки (BdsDxe и т. п.)
5. python scripts/vncgrab.py                           <- снять один кадр и посмотреть, до чего дошло
6. adb shell su -c 'dd if=/dev/block/by-name/expdb of=/data/local/tmp/e.img bs=1M'
   adb pull /data/local/tmp/e.img && grep -a "\[SBC\] image" e.img   <- цепочка проверки ATF
```
