## 0. Самый важный вывод (сразу)

**Этот файл побайтово идентичен preloader, который телефон запускает прямо сейчас.**
(sha256 раздела `preloader_raw_a`, снятого с устройства, тоже `056ed47a…`)

→ Прошив его, вы **не измените ничего**. Если бы это действительно была «инженерная сборка без
авторизации», то это устройство **уже её запускает**.

## 1. Структура контейнера

```
0x0000  MMM\x01  len=0x38  "FILE_INFO"
0x0038  MMM\x01  len=0x0C  type=1  val=1
0x0044  MMM\x01  len=0x64  type=7  val=0x90

0x00BC  MMM\x01  len=0x30  type=8  val=0

```
Поля заголовка (`parse_hdr`):
```
load = 0x02000F10   size = 0x0007A0B0   header = 0xF0   ida = 0xF0
база времени выполнения 0x02001000, код 0xF0 .. 0x7A1A0
0x384E60 байт после образа — сплошное заполнение 0x00
```

## 2. Откуда берётся SBC (Secure Boot Control) — решающее доказательство

```
0x020522FC  push   {r7, lr}
0x020522FE  mov    r7, sp
0x02052300  movs   r0, #0x1F          ; efuse word index 31
0x02052302  bl     #0x02054860        ; чтение efuse
0x02052306  ubfx   r0, r0, #1, #1     ; взять bit 1
0x0205230A  pop    {r7, pc}
```

**SBC читается из eFuse во время работы** (bit 1 слова 0x1F). eFuse — это OTP, записывается один раз;
**изменение preloader не может его изменить**.

## 3. Логика проверки исполняется «по условию», а не «обходится»

Вызывающая сторона (0x0204FA0E):
```
0x0204FA14  bl     #0x020522FC        ; r0 = sbc_en
0x0204FA18  mov    r1, r0
0x0204FA1A  movw   r0, #0x7528        ; "sbc_en = %d"
0x0204FA22  bl     #0x02045C74        ; вывести sbc_en
0x0204FA26  bl     #0x020522FC        ; прочитать ещё раз
0x0204FA2A  cbz    r0, #0x0204FA5C    ; sbc_en == 0 -> пропустить проверку целиком
0x0204FA2C  movw   r0, #0x7535        ; "sbc_en = 1"
0x0204FA34  bl     #0x02045C74        ; вывести
...                                    ; продолжить в проверку цепочки сертификатов
```

Это **нормальная розничная логика**: устройства без зажжённого SBC пропускают проверку, устройства
с зажжённым — проверяют. Никакого жёстко зашитого обхода вида `movs r0,#0` / `bx lr` нет.

## 4. Код цепочки сертификатов / проверки образа присутствует полностью

```
   0x020408D2  ->                  "cert chain vfy fail..."
   0x020408F0  bl #0x0200E368     ; настоящая точка входа проверки (0 = успех)

0x0204E888  путь img auth fail -> "img auth fail(0x%x)"
0x0204FE22  0x020676AD -> "seclib_img_auth_load_sig"
```

## 5. Проверка DA (usbdl_verify_da) тоже полная, без короткого замыкания

Функция `0x0201144C` содержит:
- проверку длины DA (сообщение об ошибке `da_len < sig_len`)
- диспетчеризацию по таблице переходов на байте типа DA (`sub.w r1, r0, #0xC4; cmp r1, #0x23; tbh [pc, r1, lsl #1]`)
- ветку специального значения `0xFE`
- возвраты при отказе вида `#-1`

**Ветки-короткого-замыкания «сразу вернуть успех» там нет.**

## Решающее измерение с нулевым риском (только чтение)

Preloader сам печатает свой вердикт:

```
0x0204FA1A  "sbc_en = %d"      -> в логе появится "sbc_en = 0" или "sbc_en = 1"
```

А лог preloader попадает в раздел **`expdb`** (128 MiB на этом устройстве).

```bash
adb shell su -c "dd if=/dev/block/by-name/expdb of=/data/local/tmp/expdb.img bs=1M"
adb pull /data/local/tmp/expdb.img
grep -a -o "sbc_en = [01]" expdb.img
```

Также можно прочитать `seccfg` (раздел состояния блокировки MTK, соответствующий строке образа
`[SEC_POLICY] lock_state = 0x%x`) и確認 `lock_state`.

## Замечание: прошивка `tee` на самом деле не зависит от «отсутствия авторизации»

- Загрузчик разблокирован (`ro.boot.flash.locked=0`) → **fastboot может писать `tee_a` напрямую**
- Но **preloader проверяет подпись ATF при его загрузке** (если SBC включён)
- Поэтому реально решает вопрос о загрузке модифицированного `tee` всё равно **SBC в eFuse**

# Результаты проверки на устройстве (2026-10-05, только чтение)

## A. Secure Boot на этом устройстве **ВКЛЮЧЁН** (измерено, а не предположено)

Сырой текст, прочитанный прямо из `expdb` (раздел лога загрузки preloader, 128 MiB):

```
   440  sbc_en = 1                  <- значение SBC, вычисленное самим preloader
   220  [PART] img_auth_required = 1
     5  img_auth_required = 0
    21  [SEC_POLICY] lock_state = 0x3
    21  cert vfy(24 ms)  / cert vfy(17 ms) / ...   <- проверка сертификатов реально выполнялась и прошла
    12  part: lk_a img: aee
    10  part: lk_a img: bl2_ext
    10  part: gz_a img: unmap2
    10  part: gz_a img: gz
```

Точно совпадает с сырыми данными раздела `seccfg`:

```
00000000: 4d4d4d4d 04000000 3c000000 03000000   MMMM....<.......
00000010: 00000000 00000000 45454545 b4c9b88a
00000020: 255a1745 17c0c5f6 85315e9e c48e00f7
00000030: c8965b9d a1ed3100 cf79a983 00000000
                    ^ 0x0C = 0x03  <- совпадает с lock_state = 0x3 в логе
        смещение 0x18..0x38 — 32-байтовый хеш seccfg
```

**Вывод**: поскольку `sbc_en = 1` и `img_auth_required = 1`, модифицированный ATF
**обязан пройти проверку сертификата MTK**, чтобы загрузиться →
**подпись через pwnage (режим LEGACY) — обязательный шаг, его нельзя пропустить.**

## B. Маршрут GenieZone в DroidVM на этом устройстве неработоспособен

```
/dev/gunyah   -> не существует
/dev/kvm      -> не существует (EL2 занят GZ)
/dev/gz_kree  -> существует (char 10,99)  <- сервисный интерфейс KRE у GZ
/dev/gzvm     -> не существует            <- интерфейс ВМ, нужный crosvm/DroidVM
```

`VMHypervisor.GENIEZONE` ищет именно `/dev/gzvm`. На этом устройстве есть только GZ старого поколения,
а в `isBackendSupported` QEMU не поддерживает GENIEZONE (поддерживает только crosvm).
→ **DroidVM может использовать только бэкенд KVM, то есть `tee` обязательно нужно прошить.**

## C. Предоставленный вами preloader не помогает

Он равен версии, которую устройство запускает сейчас (побайтово идентичен), а его решение по SBC читает eFuse:

```asm
0x020522FC  movs r0, #0x1F          ; efuse word 31
0x02052302  bl   #0x02054860        ; чтение efuse
0x02052306  ubfx r0, r0, #1, #1     ; SBC = bit 1
```

Поэтому он **не** пропускает проверку. Для «загрузки без проверки» нужен другой preloader,
вручную изменённый так, чтобы не читать eFuse.

## D. Один пункт, который всё ещё не удалось разделить (указано честно)

Явный лог проверки preloader называет только `lk_a`(aee/bl2_ext) и `gz_a`(gz/unmap2);
**`tee_a`/`atf` там прямо не появляются**. При этом внутри `bl2_ext` есть строки
`[BL31] load failed` + `atf` + `vm-BL31-reserved`, что указывает: загрузка ATF происходит на этапе
`bl2_ext`. Кто конкретно проверяет ATF и проверяет ли вообще — в этом раунде изолировать не удалось.

→ При условии `sbc_en=1` **безопасное допущение — считать, что «проверка будет».**

## E. Перекрёстная проверка: эти логи действительно от текущего preloader

В expdb присутствует только **одна** метка сборки preloader:

```
  10  Build Time: 20230918-112001
  10  20230918-112001          (метки сборки никакой другой версии нет вообще)
```

И метка сборки, встроенная в текущий образ, тоже `20230918-112001`
→ Те логи `sbc_en = 1` / `cert vfy(24 ms)` — **не остатки старой версии**, их напечатал именно этот
инженерный preloader.

## F. В чём инженерность инженерного preloader: путь DA/EDL

У `usbdl_verify_da` (0x0201144C) во всём образе **ровно одна точка вызова**: 0x02032B86.

```asm
0x02032B68  ldrb.w  r0, [r8]        ; принятый байт
0x02032B6C  cmp     r0, #0xA0       ; как DA считается только 0xA0
0x02032B6E  bne     #0x2032B96
...
0x02032B80  add     r0, sp, #0x1c
0x02032B82  mov.w   r1, #0x12c
0x02032B86  bl      #0x201144C      ; usbdl_verify_da(buf, 0x12c)
0x02032B8A  mov     r0, r4          ; <- используется r4 напрямую, БЕЗ cmp r0 / bne
0x02032B8C  mov     r1, r5
0x02032B8E  mov     r2, fp
0x02032B90  bl      #0x2045C74      ; лог
0x02032B94  b       #0x2032B30      ; назад в основной цикл
```

**Возвращаемое значение просто отбрасывается, и точка вызова не принимает никакого решения.**
(Если принудительный обход существует, то только внутри функции — где есть одна подозрительная
ветка отказа, `bl #0x2045BA8(1)`, которую в этом раунде полностью исключить не удалось.)

## G. Итоговое суждение

| Вопрос | Ответ |
|---|---|
| Отключает ли инженерный preloader **проверку образа при загрузке**? | **Нет** (SBC по-прежнему читает eFuse, измеренное значение = 1, проверка сертификата реально исполняется) |
| Мог ли он отключить **авторизацию EDL/DA**? | **Весьма вероятно** (возвращаемое значение `usbdl_verify_da` не проверяется) |
| Значит, для прошивки модифицированного `tee` всё ещё нужна подпись? | **Да.** Прошивка без авторизации ≠ загрузка без проверки |

**Способ проверить «отсутствие авторизации» с нулевым риском**: войти в EDL и неподписанным DA
сделать **только чтение** (например, `mtkclient r seccfg`) — посмотреть, потребует ли он файл `.auth`.

**Самый прямой способ увидеть «что именно изменено»**: сделать бинарный diff между стоковым
preloader xagapro и этим образом.

## J. Где ATF реально загружается

```
Load 'tee_a' partition to 0x0xffff000048200000 (283016...)
```

→ Работающий ATF — это член `atf` внутри `tee_a`, именно то, что изменяет патч NoGZ.

# Подпись завершена (2026-10-05)

## Инструменты

`kasnria001/pwnage24mtk` (публичный):
- Принцип: дефект разбора ASN.1-сертификатов в MTK (тот же класс, что CVE-2023-20696 / исправлен в CVE-2025-20730)
- Старые устройства используют `bypass_mode 1` (= обнаруженный здесь `LEGACY` / `enter-value traversal, arg4=1`)
  Подход: **исходный, неизменённый CERT2 DER** оборачивается как поддельный объект `BIT STRING` впереди,
  а настоящий сертификат ставится позади и несёт обновлённые image hash / image hdr hash
- Только стандартная библиотека, без дополнительных зависимостей

Команды:
```bash
python sign_mtk_cert.py <unsigned.img> --legacy -w -o <out.img>
python verify_mtk_image.py --all <out.img>      # требуется 2 × Result: VALID
```

## Ключевая ловушка: подписанный образ на 1072 байта больше раздела

```
без подписи : 5 242 880   (= размер раздела tee, заполняет ровно)
с подписью  : 5 243 952   (+1072)
```

Прирост даёт обёртка BIT STRING (987 B) плюс CERT2 dsize 982→2059 (выровнено до 2064).

**Но точка вставки после ATF, поэтому хвостовое нулевое заполнение полностью не изменилось:**

| Член | без подписи | с подписью |
|---|---|---|
| `atf` | 0x200 | 0x200 |
| `tee` | 0x46440 | 0x46870 (+1072) |
| `cert1` | 0x353a40 | 0x353e70 (+1072) |
| `cert2` | 0x354310 | 0x354740 (+1072) |
| хвостовое нулевое заполнение | 1 751 322 | **1 751 322 (не изменилось)** |

В хвосте 1.75 MB нулей → **обрезав 1072 байта нулей, получаем ровно 5 MiB без потери данных.**
(Проверено, что обрезаемое — всё 0x00.)

# Подтверждение из社区-руководства (Coolapk: «MTK SPFlash V6 usage tutorial for xaga/pearl»)

Ключевые цитаты из руководства:

> Поскольку инженерный **Preloader открывает небезопасный порт VCOM и отключает проверки SLA
> (аутентификация последовательного канала) и DAA (аутентификация агента загрузки)**, это позволяет
> прошивать устройство инструментами без авторизации учётной записи сервисного центра Xiaomi

> Недавно хорошая новость: **файл загрузки инженерного Preloader для xaga утёк**. Чем это полезно?
> Ответ: **бесплатное спасение кирпичей** … позволяет избежать некоторых «глухих» кирпичей и спасти
> устройство самому, не платя

## Три независимых свидетельства полностью согласуются

| Что говорит руководство | Соответствующее доказательство в этом образе |
|---|---|
| **DAA** (аутентификация агента загрузки) отключена | **возвращаемое значение `usbdl_verify_da` просто отбрасывается** (§F) |
| Открыт небезопасный порт **VCOM** | в образе есть строка `USB CDC ACM for preloader` |
| Речь лишь о «возможности записать», а не об отключении проверки | `sbc_en` читается из eFuse, измерено = 1, `[SBC] image atf header auth pass` (§E/§H) |

→ **Инженерный preloader = делает «запись» не требующей авторизации (+ спасает кирпичи),
и вообще не касается того, «проверяется ли при загрузке».** Согласуется с §G/§I, противоречий нет.

## Два полезных для нас пункта из руководства

1. **Полная прошивка через SP Flash заново блокирует загрузчик**
   > после глубокой прошивки bl становится заблокированным, хотя со второго раза можно открыть мгновенно
   > (некоторые говорят, что если не прошивать раздел seccfg, состояние разблокировки bl сохранится, но инструмент этот раздел не прошивает)
   → **Не прошивайте `tee` через SP Flash**, иначе загрузчик снова заблокируется и fastboot станет неудобным.

2. Прошивка инженерного preloader идёт через **fastboot**:
   ```
   fastboot flash preloader1 preloader_xaga.bin
   fastboot flash preloader2 preloader_xaga.bin
   fastboot reboot
   ```
   (На этом устройстве by-name разделы — `preloader_raw_a` / `preloader_raw_b`)

3. Материалы, нужные для цепочки восстановления (пакет, которым в руководстве поделился @rkpsz):
   `SP_Flash_Tool_v6.2316_Win.zip` + `auth_sv5.auth` + `libusb_v1.12.exe` +
   драйвер MediaTek + `preloader_xaga.bin` + пакет прошивки `flash.xml`

## (1) crosvm + KVM: **стабильно работает** (измерено)

Через встроенный AVF crosvm загружено ядро microdroid: гость стартовал полностью, SMP на двух ядрах удался.

## (2) QEMU из комплекта DroidVM + KVM: **нестабильно (гонка big.LITTLE)**

Запуск QEMU «как есть» падает, потому что пространство имён линковщика не находит `libbinder_ndk.so`;
нужен обход через `LD_LIBRARY_PATH=/system/lib64` (сам демон DroidVM имеет правильное окружение и не нуждается в этом).

```
Accelerators supported in QEMU binary: gunyah, kvm, tcg     <- geniezone отсутствует
```

`QemuBackendInstance` в DroidVM жёстко задаёт cpu как `host[,pmu=off]` (исходник L196-201), и измерено:
**одна и та же команда, 5 запусков: 2 успеха / 3 отказа**:

```
qemu-system-aarch64: Failed to put registers after init: Invalid argument
```

**Первопричина (установлена)**: `-cpu host` перечисляет возможности **того CPU, на котором QEMU сейчас
находится**; на big.LITTLE миграция между A55 и A78 во время записи регистров vCPU → EINVAL.

Проверка привязки:

| Условие | Результат |
|---|---|
| Без привязки × 5 | 2/5 успешно |
| `taskset 1` (cpu0, A55) × 3 | **3/3 успешно** |
| `taskset 80` (cpu7, A78) × 3 | **3/3 успешно** |

Поведение разных вариантов `-cpu` (нестабильно; случайность доминирует над различиями в возможностях):
`host` ✗ · `host,pmu=off` ✗ (60%) · `host,sve=off` ✓ · `host,pauth=off` ✓ ·
`host,sve=off,pauth=off` ✗ · `host,sve=off,pmu=off` ✓ · `max` ✗ · `cortex-a55` ✗ (KVM поддерживает только host/max)

**Вывод**: QEMU+KVM внутри DroidVM требует **привязки к ядрам** для надёжности; crosvm — нет.

## (3) Побочное доказательство, не связанное с патчем ATF

Features в `/proc/cpuinfo` **полностью одинаковы** до и после прошивки (в обоих случаях нет `sve`),
что показывает: патч не изменил определение возможностей CPU ядром.
