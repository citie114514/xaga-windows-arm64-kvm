## 1. 🔴 ESP が空 —— ファームウェアが起動可能なデバイスを見つけられない

**症状**
```
BdsDxe: No bootable option or device was found.
```
または UEFI 画面で止まる / UEFI Shell に落ちる。

**原因**
Dism++ などでイメージを展開すると、**ESP にブートファイルが書かれません**。フォーマット直後の
ESP にはこれしかありません：

```
EFI\Boot\BOOTAA64.EFI                     MISSING
EFI\Microsoft\Boot\bootmgfw.efi           MISSING
EFI\Microsoft\Boot\BCD                    MISSING
```

**解決**
```powershell
bcdboot G:\Windows /s S: /f UEFI /v
```
x64 の `bcdboot` でも ARM64 イメージに**ブートファイルを書けます**（`bootaa64.efi` を自動選択）。
書いた後、`bootmgfw.efi` の PE machine が **`0xAA64`** であることを確認してください。

詳細は [03-windows-vm.md](03-windows-vm.md) の 2.3 節。

## 2. 🔴 VNC のポートは思っているものではない

**症状**
`adb forward tcp:5900 tcp:5900` しても VNC クライアントが繋がらない / 繋がっても真っ黒。
しかし**たまに繋がる**ので挙動が読めない。

**原因（2 層）**

1. `-vnc 127.0.0.1:N` の **`N` は display 番号であってポート番号ではない**。ポート = `5900 + N`
   → `-vnc 127.0.0.1:5900` と書くと実際は **11800** をリッスンする ✗（5900 ではない）
2. **ポートが埋まっていても QEMU はエラーを出さず**、**黙って display 番号を +1 する**
   → 5900 にいるつもりが実際は **5901** ✗

**解決**

```bash
# 正しい書き方：:0 → ポート 5900
-vnc 127.0.0.1:0,lossy=on
```

**さらに**、起動前にポートが本当に空くのを待ち、起動後に実際のポートを確認します：

```bash
# 起動前
for i in $(seq 1 30); do
    netstat -tln | grep -q ":5900 " || break
    sleep 1
done

# 起動後
netstat -tlnp | grep qemu        # 127.0.0.1:5900 と出なければならない
```

`scripts/phone/boot-win.sh` はこの両方を実施し、**確認に失敗したらそのまま終了します**。

## 3. 🔴 big.LITTLE 上で `-cpu host` がランダムに失敗する

**症状**
```
qemu-system-aarch64: Failed to put registers after init: Invalid argument
```
同じコマンドを 5 回連続で実行すると、成功したり失敗したりする。

**原因**
`-cpu host` は **QEMU がたまたま動いている CPU** の機能を列挙します。MTK は 4×A78 + 4×A55 なので、
vCPU レジスタを書いている最中にスケジューラが A55/A78 間でマイグレーションすると `EINVAL`。

**実測データ**

| 条件 | 成功率 |
|---|---|
| アフィニティなし | **2/5** ✗ |
| `taskset 1`（cpu0、A55） | **3/3** ✓ |
| `taskset 80`（cpu7、A78） | **3/3** ✓ |
| `taskset f0`（cpu4-7、A78 クラスタ） | **3/3** ✓ |

**解決**
```bash
taskset f0 qemu-system-aarch64 ...
```

> 各種 `-cpu` の変種（`host,pmu=off`、`host,sve=off` など）は**挙動が不安定で、
> 機能差よりランダム性の方が支配的**です。機能をいじって回避しようとせず —— **とにかく
> アフィニティを固定してください**。

## 4. 🔴 `pkill -f` が自分のシェルを殺した

**症状**
スクリプトが途中で何の出力もなく消え、プロセスも立ち上がっていない。

**原因**
```bash
adb shell su -c 'pkill -f qemu-system-aarch64.real; ...'
```
`pkill -f` は**コマンドライン全体**にマッチし、**外側の `su -c` のコマンドラインにその文字列が
含まれている** → **自分のシェルも殺してしまう**。

**解決**
**短いプロセス名**でマッチする（`pkill` は既定でプロセス名だけを見ます）：

```bash
pkill qemu-system-aar
```

または `pkill` を**スクリプトファイル**の中に入れて実行する（スクリプト自身のコマンドラインには
その文字列が含まれない）：

```bash
# scripts/phone/stop-vm.sh
pkill qemu-system-aar
```

## 5. 🟠 `-device usb-tablet,bus=usb` がバスが無いと言う

**症状**
```
qemu-system-aarch64: -device usb-tablet,bus=usb: Bus 'usb' not found
```
QEMU が起動すらしない。

**原因**
`-device qemu-xhci,id=usb` の `id=usb` は**単なるデバイス id** で、USB バス名は **`usb.0`**
（`<id>.0`）です。

**解決**
**`bus=` を外す**だけで、唯一の USB コントローラに自動でぶら下がります（一番楽）：

```bash
-device qemu-xhci,id=xhci -device usb-tablet -device usb-kbd
```

## 6. 🟠 Windows インストール ISO を挿すと起動を奪われる

**症状**
システムは入っているのに、起動すると Windows インストーラーに入る。

**原因**
Windows インストール ISO は**起動可能**（El Torito + `EFI\BOOT\BOOTAA64.EFI`）なので、
UEFI がそちらを優先することがあります。

**解決**
- インストール後は Windows インストール ISO を**挿さない**
- 光学ドライブが欲しければ **`virtio-win.iso`** を挿す —— あれは**純粋なデータディスク**
  （`genisoimage` 製 ISO9660。El Torito も EFI ディレクトリも無い）なので**挿しても安全**

## 7. 🟠 `adb push` で `/data/media/0/` が権限拒否される

**症状**
```
adb: error: stat failed when trying to push to /data/media/0/DroidVM/win.vhdx: Permission denied
```

**原因**
`/data/media/0` は root 専用ディレクトリで、adb の shell ユーザーでは書き込めません。

**解決**
shell が書ける場所に先に転送し、`su` で移動する（**同一ファイルシステム内なら一瞬の rename**）：

```bash
adb push win.vhdx /data/local/tmp/win.vhdx
adb shell su -c 'mv /data/local/tmp/win.vhdx /data/media/0/DroidVM/'
```

> 余談：`/storage/emulated/0/...` は **FUSE マウント**、`/data/media/0/...` は**ネイティブパス**で、
> 同じファイルを指します。QEMU がネイティブパスを使えば FUSE 層を迂回できます。
> （実測の読み出し速度はどちらも約 950 MB/s で大差ありませんが、ネイティブの方が安定します。）

## 8. 🟠 ゲスト内の時刻が 2768 年になる

**症状**
Windows のタスクバーが `2768/12/24` と表示する。

**原因**
QEMU 側の RTC 初期値の読み取りにズレがあります（**+742 年**）。
ただし **PL031 RTC は 32 ビット秒カウンタで、物理的に 2106 年までしか表現できません** ——
つまり**RTC が出した値であるはずがなく**、QEMU ビルドの変換バグです。

**解決**
**ネットワークが繋がれば Windows の NTP が自動で補正します**（これはネットワークが通っている
証拠にもなります）。手動で直すなら：

```powershell
# Windows 内、管理者 PowerShell
Stop-Service w32time; Set-Service w32time -StartupType Disabled
Set-Date -Date "2026-10-06 03:20:00"
```

またはタスクバーの時計を右クリック → 日付と時刻の調整 →「時刻を自動的に設定する」をオフ → 手動で変更。

## 9. 🟠 DroidVM の設定体系：必ず切り分けるべき 3 つのこと

DroidVM アプリと QEMU コマンドラインは**互いに相容れない 2 つの起動方法**です。混ぜると必ず踏みます。

### (a) アプリが作る設定は**それ自体では動かない**

DroidVM が生成する起動引数は不完全です：

- **virtio NIC に `-netdev` バックエンドが無い** → ゲストにネットワークが無い
- **`virtio-balloon` が無い** → メモリが増える一方

**解決**：**ラッパースクリプト**を 1 枚入れて、アプリが呼ぶ `qemu-system-aarch64` を
本物の `.real` に転送しつつ足りない分を補います —— 詳しい導入手順は
[scripts/phone/README.md](../../scripts/phone/README.md)。
**呼び出し側が指定していない場合にだけ補う**ので、自分で書いた起動スクリプトを邪魔しません。

### (b) VNC ポートは既定で**ランダム**

`vms.json` の `screens.*.vnc.port` の既定値は **`-1`** =「自動で選ぶ」：

```json
"vnc": { "host": "127.0.0.1", "port": -1, "password": "", "password_auth": false }
```

**結果**：起動のたびにポートが変わり得ます ✗ —— `adb forward tcp:5900` した先には誰もいません ✗。
「VM は起動しているのに VNC が繋がらない」のよくある原因です。

本プロジェクトは**この道を回避します**：`boot-win.sh` が `-vnc 127.0.0.1:0`（= 5900）を
ハードコードし、起動後に実際のポートを再確認します。

> `port` フィールドを固定値にするのも**理論上は別解ですが未検証**で、下の (c) のリスクがあるため、
> 本プロジェクトのスクリプトはそれに依存していません。

### (c) `vms.json` を手で編集するとアプリが読めなくなる

**症状**
`vms.json` を手で編集（例：ディスクパスの変更）したら、VM がアプリから**消えてしまい**、
「現在のバージョンでは読み取れません」と出る。

**原因**
DroidVM は独自の厳格なスキーマで検証しており、**手で追加したフィールドを認識しない**ため、
エントリごと除外してしまう。

**解決**
- **既にあるフィールドだけを変更する**（例：`disks[].path`、`screens.*.exporter`）—— **新しいフィールドは追加しない**
- 元の所有者とパーミッションを保つ：
  ```bash
  OWN=$(stat -c %u vms.json); GRP=$(stat -c %g vms.json); MODE=$(stat -c %a vms.json)
  # ... 編集 ...
  chown $OWN:$GRP vms.json; chmod $MODE vms.json
  ```
- **編集前にバックアップ**：`cp vms.json vms.json.bak`

### 結論：どちらか一方、混ぜない

| 経路 | 長所 | 短所 |
|---|---|---|
| **`boot-win.sh` コマンドライン**（推奨） | 引数を完全制御、ポート 5900 固定、アプリに左右されない | GUI が無く、引数の変更はスクリプト編集 |
| **DroidVM アプリ起動** | GUI があり、複数台を管理できる | 引数が不完全（ラッパー必須）、ポートがランダム、設定を手で編集できない |

> **両方を同時に使わないでください**：アプリ起動は `vms.json` を書き換え、コマンドライン起動は
> 一切触りません。

## 10. 🟡 `virtio-gpu-rutabaga-pci` が即クラッシュする

**症状**
```
exit=139      # SIGSEGV
```
QEMU が何も出力せず即死。

**原因**
`virtio-gpu-rutabaga-pci`（gfxstream 経路）+ `-display egl-headless` がこのビルドでセグフォルト。
ちなみに `virtio-gpu-gl-pci` + `-display none` も
`The display backend does not have OpenGL support enabled` を出します。

**解決**
- 通常の表示には **`virtio-gpu-pci`**（Windows は `viogpudo` を使う）
- **virgl**（Linux ゲストでのみ意味がある）には **`virtio-gpu-gl-pci` + `-display egl-headless`**（初期化成功を実測）
- **rutabaga は使わない**

## 11. 🔴 **ROM / OTA 書き込み後にパッチが無効になる**

**症状**
新しい ROM を焼いたら `/dev/kvm` が消えた —— あるいは**別のファームウェアで作ったパッチ**を
`tee_a` に書いて、**起動が止まったように見える**（⚠️ ただし先に第 12 項を読んでください ——
パッチ書き込み直後の初回起動は本来 2 分ほど 2 回目の画面で止まります ✗）。

**原因**
NoGZ パッチが変更するのは `tee` パーティション内の `atf` メンバの起動引き渡しロジックなので、
**パッチは「ビルド時に使った `tee` ベース」にのみ有効**です。

実測（同じ Redmi Note 11T Pro+、2 台を比較）：

| デバイス | `tee_a` | `lk_a` | 結果 |
|---|---|---|---|
| 1 台目 · Android 15 純正 ROM | `f8f286f1…` → パッチ `f1511dca…` を書き込み | `8cbaa2e8…` | ✅ 起動 + KVM |
| 1 台目 · **Android 16** へ更新 | パッチ `f1511dca…`（**不変**） | **`a17d87c6…`（変化！）** | ✅ **依然として起動 + KVM** |
| 2 台目 · **別のファームウェアバッチ** | ROM により `a91f5ded…` へ更新 | `a17d87c6…` | 1 台目のパッチを書き込み → 起動停止に見えた ⚠️ |

> ⚠️ **この表は「同ベース」と「ベース違い」をはっきり区別して読む必要があります** ——
> ここが最も誤読されやすい点です：
>
> | | 1 台目 | 2 台目 |
> |---|---|---|
> | 書き込むパッチのベース | `f8f286f1…`（rk パッチ）| `f8f286f1…`（rk パッチ）|
> | 書き込み前の自分の `tee_a` | **`f8f286f1…`** | **`a91f5ded…`** |
> | 判定 | ✅ **同ベース** | ❌ **ベース違い** |
>
> **したがって 1 台目の成功を「ベース違いでも可能」の証拠にはできません** ✗ ——
> あれは「**同ベースなら使える**」を証明しているにすぎません ✓。
> **真にベース違いなのは 2 台目の 1 回だけ** ⚠️（しかもその結論は不確か。下記参照）。

**結論（直感に反するが、実測はこう）**：

- ✅ **`lk` が変わってもパッチに影響しない**（1 台目の `lk_a` は差し替わったが動く）
- ✅ **`gz` / `dtbo` / `boot` / `system` が変わっても影響しない**（Android 15 → 16 をまたいで正常）
- ❌ **`tee` ベースが変わると無効になる** —— これが唯一の既知の「急所」
- ⚠️ **同じファームウェアバッチならベースも同じ**。バッチが違えば異なり得る（本件で上流 `xaga`
  profile のベース `bd4b13a7…` は 3 つ目のバッチ）；**「1 台ごとに違う」わけではない**

> 🛠 **重要な訂正（2026-10-06）**：上の表の最終行「起動停止」は**根拠が不確か**でした。
> 後の実測で、**パッチ書き込み後は毎回の起動で本来 2 回目の画面で 2 分近く止まる**ことが
> 分かりました（第 12 項）。当時は待ち時間が足りずに死刑宣告してしまいました ✗。
> 2026-10-07 の実験でこの懸案は決着しました：**ベース違いでも【正常に起動します】** ✓
> —— 「必ず壊れる」✗ でも「未検証」⚠️ でもなく、**実測で使える** ✓（[tee/README.ja.md](../../tee/README.ja.md) 参照）。
> 自分のベースに合わせたパッチを推奨するのは今も正しい ✓ ですが、理由は**TEE OS のバージョン
> 整合**であり、2 回目の画面で止まるからではありません。

**最も厄介な点：ROM パッケージに `tee` イメージが無くても書き換わる**

2 台目に焼いた ROM には **`tee` イメージが入っていませんでした**が、焼いた後 `tee_a` は
`f8f286f1…` から `a91f5ded…` へ変わっていました（初回起動時のファームウェア更新か
`super.img` が原因と思われます）。
**したがって「パッケージに tee が入っているか」で書き換わるかどうかは判断できません。**

**解決**

```bash
# ① ROM を焼く前にバックアップ
adb shell su -c 'dd if=/dev/block/by-name/tee_a of=/data/local/tmp/tee_a.bak bs=4096'

# ② 焼いた後にハッシュを計算し、パッチの「対応ベース」と突き合わせる
adb shell su -c 'dd if=/dev/block/by-name/tee_a bs=4096 2>/dev/null | sha256sum'
```

| 結果 | 次の一手 |
|---|---|
| 変わっていない | ✅ パッチは有効なまま。何もしなくてよい |
| 変わった | ❌ パッチ無効 → **新しい `tee_a`/`lk_a`/`preloader_raw_a` を dump して再ビルド**（他 ROM の完成品は使えない）|

**ベースが変わったかどうかの一番楽な確認方法** —— 触られていない側のスロットを見る：

```bash
adb shell su -c 'dd if=/dev/block/by-name/tee_b bs=4096 2>/dev/null | sha256sum'
# = f8f286f1… → ベースは変わっていない ✓
```

**ロールバック**：バックアップした `tee_a` を書き戻す。または B スロットへ切り替える
（`tee_b` は一度も変更されていないので天然の保険）。

## 12. 🔴 **パッチ書き込み後の毎回の起動で 2 回目の画面が約 2 分止まる —— 文鎮ではない！**

**症状**
NoGZ パッチを書いて再起動すると、**起動 2 回目の画面**（logo2 / スピナー）で
**1〜2 分まったく動かない** ✗ —— 完全に「文鎮化」に見えます。

**しかしこれは正常です** ✓ —— 実測（2 台目、`tee_a` に `17ec8497…` を書いて再起動）：

```
 20s   adb にはすでにデバイスが見えるが sys.boot_completed=0
 30s   ...
 140s  まだ待機中（120 秒間、画面はまったく変化なし）
 150s  sys.boot_completed=1   ← 自力で起動した ✓
```

**結果**：`/dev/kvm` は正常に出現 ✓、システムは無傷 ✓、497 個のアプリパッケージが 1 つも
欠けていない ✓

**原因（推測）**
パッチにより ATF が EL2 を GZ に渡さなくなり、起動チェーンのどこかが **GZ の応答を待って**いて、
来ないのでタイムアウトして先へ進む —— つまり「止まるが死なない」。

### ✅ 正しい対応：**3 分待つ**

- **文鎮だと思わないこと** ✗
- **絶対に**慌てて「音量下 + 電源」で fastboot に入らないこと ✗ ——
  **それこそが起動を中断させます** ✗。本来成功する初回起動を、本当に起動できない状態に変えます ✗
- **5 分以上**まったく変化がない場合にのみ、別ベースのパッチを書いた疑いを持ってください ✗

**これは一度きりの現象ではありません** —— パッチがある限り、毎回の起動でこの待ちが発生します ✓
（GZ が EL2 を取れないため、起動チェーンが毎回あのハンドシェイクのタイムアウトを待つ、と考えればよいです）。

### 「正常な遅さ」と「本当の故障」の見分け方

| 現象 | 正常な遅さ ✓ | 本当の故障 ✗ |
|---|---|---|
| 画面 | **2 回目**の画面（logo2）でスピナー | **1 回目**の画面で停止、またはブラックアウト後に**自動で fastboot** |
| adb | **デバイスが見える**（`adb devices` にシリアルが出る） | 見えない、または既に fastboot モード |
| 時間 | 1〜3 分で自力で起動 | 5 分以上変化なし |
| 対応 | **待つ** ✓ | バックアップを書き戻す（[tee/README.md](../../tee/README.ja.md) のロールバック節）|

> 💡 教訓：本プロジェクトは待ち時間が足りず、これを本物の文鎮と誤認して無駄な復旧を 1 回行いました。
> **パッチ書き込み後の初回起動には、まず 3 分与えてください。**

### 🔑 「2 回目の画面で止まる」が重要な判据になる理由

ATF の署名検証は **`bl2_ext` 段階**（preloader 段階、**カーネル起動より遥か前**）で行われます：

```
ATF 検証（[SBC] image atf header auth pass）
    ↓ カーネルより前
カーネル起動 → 1 回目の画面 → 2 回目の画面
```

**したがって：**

```
2 回目の画面が見えない（1 回目で停止 / 直接 fastboot）
    ⇒ 「受け入れられなかった」可能性 —— 署名 / ベース / パーティション書き込みの破損

2 回目の画面（logo2）が見える
    ⇒ ATF は間違いなく受け入れられている ✓
    ⇒ 問題は署名でもベースでもなく、その後の起動過程にある
      （つまり遅延、または TEE の初期化）
```

> この判据は**タダ**です：ログも PC も不要で、**画面だけで切り分けられます** ✓
> 本プロジェクトが後に「あの起動停止は単に待ち時間不足だった」と確認できたのも、このおかげです ✓

## 付録：落とし穴に見えてそうでないもの

| 現象 | 真実 |
|---|---|
| `warning: nic virtio-net-pci.0 has no peer` | NIC にバックエンドが無い（`-netdev user,id=n0` が欠けている）。警告だけだが**ネットワークは通らない** |
| AAVMF が起動前に数十秒止まる | 内蔵の既定エントリ `Boot0002 "UEFI Misc Device"` が先にタイムアウトするだけで正常 |
| 初回起動中に画面が一瞬暗くなる | Windows が再起動/表示モード切替をしている。**VNC を繋ぎ直せばよい**。進捗は失われない（ディスクに書かれている） |
| `Trusted root check: skipped` | オフライン署名検証はトラストルート比較を省略する。**実機起動でしか証明できない**（失敗ではない） |
| `/dev/kvm` が `Invalid argument` | これは**正常**！`open()` は SELinux（Enforcing）を通過済みで、単に引数が無いだけ |
| QEMU が `libbinder_ndk.so` を見つけられない | DroidVM の QEMU には `export LD_LIBRARY_PATH=/system/lib64` が必要 |

## トラブルシュートの順序

「起動しない」ときは、この順に確認します：

```
1. adb shell su -c 'ls -l /dev/kvm'                    ← KVM があるか（前提条件）
2. adb shell su -c 'cat /data/local/tmp/boot.out'      ← 起動スクリプトの出力（ポート確認を含む）
3. adb shell su -c 'cat /data/local/tmp/win-qemu.log'  ← QEMU 自身のエラー
4. adb shell su -c 'cat /data/local/tmp/win-serial.log'← ファームウェアのシリアル出力（BdsDxe など）
5. python scripts/vncgrab.py                           ← 1 フレーム取得してどこまで進んだか見る
6. adb shell su -c 'dd if=/dev/block/by-name/expdb of=/data/local/tmp/e.img bs=1M'
   adb pull /data/local/tmp/e.img && grep -a "\[SBC\] image" e.img   ← ATF 検証チェーン
```
