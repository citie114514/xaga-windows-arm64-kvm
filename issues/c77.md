## Update: the crosvm backend also rejects a standard AAVMF firmware (format mismatch)

Related to the QEMU-side investigation: the standard Ubuntu/Debian AAVMF build (`qemu-efi-aarch64` `2026.05-2ubuntu2`, `/usr/share/qemu-efi-aarch64/QEMU_EFI.fd`, 3 145 728 bytes) is **not** usable as `boot.uefi.firmware` for the crosvm backend, because crosvm loads the positional argument as a kernel/bootloader image:

```
ERROR crosvm] exiting with error 1: the architecture failed to build the vm
Caused by:
    kernel could not be loaded: invalid magic number
```

That is expected — `QEMU_EFI.fd` is a raw flash-descriptor image, not PE/COFF, whereas the shipped `edk2-qemu.fd` / `edk2-gunyah.fd` are apparently rebuilt in a form crosvm accepts (they load and print their banner).

So this issue cannot be worked around by substituting a distribution firmware: fixing it needs a **PE/COFF EDK2 build that includes the ISO9660/El Torito stack**, which is exactly what the shipped `edk2-gunyah.fd` appears to be missing.

For anyone hitting both issues, the practical path today is the QEMU backend with a standard AAVMF firmware (see the QEMU firmware issue) rather than the crosvm backend.
