## Update: root cause identified — the shipped `edk2-qemu.fd` is the problem, not the invocation

I replaced the firmware with the **standard Ubuntu/Debian AAVMF build** (`qemu-efi-aarch64`, package version `2026.05-2ubuntu2`, `/usr/share/qemu-efi-aarch64/QEMU_EFI.fd`, 3 145 728 bytes) and pointed `boot.uefi.firmware` at it. **Everything else was left exactly as DroidVM generates it.**

Same command line, same `-bios` loading path, same `-machine virt`, only the firmware file replaced:

```
UEFI firmware (version 2026.05-2ubuntu2 built at 15:07:27 on Aug 26 2026)
BdsDxe: loading Boot0002 "UEFI QEMU QEMU CD-ROM " from PciRoot(0x0)/Pci(0x1,0x0)/Scsi(0x0,0x0)
BdsDxe: starting Boot0002 "UEFI QEMU QEMU CD-ROM " from PciRoot(0x0)/Pci(0x1,0x0)/Scsi(0x0,0x0)
```

The firmware now initialises its console, enumerates the SCSI CD-ROM and starts loading the Windows 11 Arm64 installer. With the shipped `edk2-qemu.fd` the same line produced only `ab=000 c=400 1234564` and a spinning vCPU.

The two files are the same size but not the same build:

```
sha256 QEMU_EFI.fd      (AAVMF 2026.05-2ubuntu2) = 0329acaa424591d81f7c5f744af1625a021d0bb37da6784a2a8ae68066fe4527
sha256 edk2-qemu.fd     (shipped)                = ca5800d2328d8f4ecea41a329a454b48acd62854a1c4ce20237f38a601a9a002
differing bytes: 1 346 232 of 3 145 728, first at offset 0x0
```

### Suggested fix

A standard AAVMF build (`QEMU_EFI.fd`) works when handed to `-bios`, so either ship one, or rebuild `edk2-qemu.fd` from a known-good AAVMF configuration and verify it reaches `BdsDxe` before release. A smoke test that greps the guest's serial for `BdsDxe` (and fails the build otherwise) would have caught this.

### Note on `-bios` vs pflash

`-bios` is fine for this firmware — no pflash drives are needed once the firmware is a working AAVMF build, so issue #80's pflash problem can be avoided entirely by *not* enabling `boot.uefi.vars_enabled` for the QEMU backend (the variable store is then simply not persisted).

### Workaround for users until this is fixed

```json
"boot": { "protocol": "uefi", "uefi": { "firmware": "<path to a standard AAVMF QEMU_EFI.fd>", "vars_enabled": false, ... } }
```

On Debian/Ubuntu hosts the firmware is one `apt download qemu-efi-aarch64` away, and the file can be pushed anywhere readable by the app.
