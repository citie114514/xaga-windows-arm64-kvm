# ⭐ Пример, проверенный на реальном устройстве

## [`tee_nogz_rk_5M.img`](tee_nogz_rk_5M.img) — **KVM работает на реальном устройстве**

```
sha256   f1511dcad9820397abb1dc843d8fa70f6284f3c3c58aa4bedd7c8c49b54d1689
base     f8f286f138e758a59159fccb4c9533355616aa1670aada795dd80402fdec5062
size     5 242 880 байт (ровно заполняет раздел tee)
cert     LEGACY
```

**Журнал проверок** (одно и то же устройство, через два крупных обновления ОС)

| Момент | Система | `tee_a` | `lk_a` | Результат |
|---|---|---|---|---|
| Первая запись | HyperOS (Android 15) | `f8f286f1…` → записан патч | `8cbaa2e8…` | ✅ появился `/dev/kvm`, Linux-гость на 2 vCPU загрузился полностью |
| После обновления | **Android 16 / HyperOS 3.3** | патч на месте | `a17d87c6…` (**заменён**) | ✅ **по-прежнему работает**, `/dev/kvm` на месте |

**Это обновление случайно дало ключевой вывод**:

> **Замена `lk` вообще не влияет на патч. Совместимость определяет только база `tee`.**

**Доказательства (сырой вывод)**

```console
$ adb shell su -c 'for p in tee_a tee_b; do printf "%s " $p; dd if=/dev/block/by-name/$p bs=4096 2>/dev/null | sha256sum | cut -c1-16; done'
tee_a f1511dcad9820397      ← этот патч
tee_b f8f286f138e758a5      ← штатный, не изменялся

$ adb shell su -c 'ls -l /dev/kvm'
crw-rw-rw- 1 root root 10, 232 2026-10-06 21:52 /dev/kvm      ← ✅

$ adb shell "grep -i kvm /proc/misc"
232 kvm

$ adb shell su -c 'dmesg | grep -i sbc'
[SBC] image atf header auth pass
sbc_en = 1
```

**Что реально запускалось**: `crosvm` (microdroid) с гостем — успешно;
`qemu-system-aarch64 -accel kvm` с Linux-гостем на 2 vCPU — успешно.
Позже на этом же устройстве **Windows 11 ARM64 была полностью установлена вплоть до рабочего стола**.

> ⚠️ Внимание: **этот патч действителен только для устройств с `tee_a` = `f8f286f1…`.**
> Перед записью **обязательно выполните самопроверку ниже**.

## 👉 Самопроверка перед записью

В репозитории есть скрипт самопроверки [`verify.sh`](verify.sh):

```bash
bash tee/verify.sh                 # автоматически определит подключённое устройство
bash tee/verify.sh <serial>        # указать устройство явно
```

Он выведет `tee_a` / `tee_b` вашего устройства и скажет, **какой готовый патч можно использовать**.

Ручной вариант (сравнить один хеш):

```bash
adb shell su -c 'dd if=/dev/block/by-name/tee_a bs=4096 2>/dev/null | sha256sum'
```

| sha256 вашего `tee_a` | Что можно записать |
|---|---|
| `f8f286f1…` (штатная база) | `tee_nogz_rk_5M.img` ✓ |
| `a91f5ded…` | `tee_nogz_shuilanA15_5M.img` ✓ |
| любой другой | ✗ **не записывать**, соберите свой по [docs/02](../docs/02-build-and-sign.md) |

## ❓ Влияет ли запись на проверки целостности приложений? (Ответ измерен: **нет**)

Это первый вопрос, который стоит задать перед записью. Мы провели **сравнение «до/после» на
одном устройстве + A/B-сравнение двух устройств**.

**Почему это не может повлиять, архитектурно**: патч делает ровно одно — **не отдаёт GZ уровень EL2**.
Всё, на что опираются проверки целостности, работает в **TEE (S-EL1)** — это совершенно отдельный
мир от EL2:

| Возможность безопасности | Кто реально обеспечивает | После патча |
|---|---|---|
| **Аппаратные ключи / аттестация KeyMint** | `keymint@1.0-service.beanpod` (TEE производителя) | ✅ работает |
| **Gatekeeper** (проверка пароля блокировки) | TEE | ✅ работает |
| **Widevine / DRM** | `widevine_driver`, держащий ссылку на `mtk_sec_heap` | ✅ работает |
| **Отпечаток / лицо** | TEE | ✅ работает |
| **Secure Element** (оплата NFC) | `secure_element@1.2-service-mediatek` | ✅ работает |
| **GZ / GenieZone (EL2)** | Фреймворк виртуализации EL2 от MediaTek | ⚠️ **не работает** (но влияния не обнаружено) |

### Доказательства

Два устройства (**одно штатное, одно пропатченное**) выполняли одни и те же команды —
результаты **совпали по всем пунктам**:

```
① Состояние Verified Boot
   ro.boot.verifiedbootstate   orange      <- у обоих orange (загрузчик разблокирован)
   ro.boot.flash.locked        0           <- у обоих 0
   ro.secure / ro.debuggable   1 / 0       <- полностью одинаково
   ro.build.tags               release-keys

② Ключевые HAL-сервисы (одинаково у обоих)
   android.hardware.security.keymint.IKeyMintDevice/default               ✓
   android.hardware.security.keymint.IRemotelyProvisionedComponent/default ✓
   android.service.gatekeeper.IGateKeeperService                          ✓
   сервисы fingerprint / biometric / auth                                  ✓

③ Жив ли TEE на самом деле (одинаково у обоих)
   присутствуют teei_daemon и потоки ядра [teei_*]     <- Trustonic TEE работает
   процесс keymint@1.0-service.beanpod работает
   android.hardware.secure_element@1.2-service-mediatek работает
   widevine_driver по-прежнему держит ссылку на mtk_sec_heap  <- путь защищённой памяти DRM жив

④ Сквозной тест аппаратного ключа (keystore_cli_v2, одинаково у обоих)
   generate --seclevel=tee   ->  GenerateKey: success
   get-chars                 ->  все характеристики в разделе "Hardware:", раздел "Software:" пуст
   sign-verify               ->  Sign: 256 bytes.  Verify: OK
```

**Как объективно убедиться, что TEE действительно работает** (а не деградировал до программной
реализации):

```bash
# Принудительно создать ключ в TEE и посмотреть, куда отнесены характеристики
adb shell 'keystore_cli_v2 generate --name=t --seclevel=tee'
adb shell 'keystore_cli_v2 get-chars --name=t'      # всё должно быть под "Hardware:"
adb shell 'keystore_cli_v2 sign-verify --name=t'    # должно быть Verify: OK
adb shell 'keystore_cli_v2 delete --name=t'
```

### Два важных замечания

1. **`verifiedbootstate = orange` (разблокированный загрузчик) сам по себе убивает Play Integrity**
   и **никак не связан** с записью `tee`. На устройстве с разблокированным загрузчиком и root
   проверки `MEETS_DEVICE_INTEGRITY` / `MEETS_STRONG_INTEGRITY` **и так не проходят**, а банковские
   приложения и так обходят это сокрытием root.
   **Запись `tee` ни улучшает, ни ухудшает это состояние** — она не касается блокировки загрузчика,
   root и dm-verity.

2. **Модули ядра `gz_*` всё равно загружаются** (в `lsmod` видны `gz_main_mod`, `gz_irq_mod`,
   `gz_virtio_mod` и другие), но счётчик ссылок равен 0 — они загружаются, но **не могут получить
   EL2 и потому мертвы**. Реально работает TEE, а не GZ.

> **Одной строкой**: патч меняет **владельца EL2** и не касается **TEE**.
> Все проверки вида «настоящее ли это устройство / не изменено ли оно» смотрят на TEE и
> Verified Boot — и ни то, ни другое не меняется.

## 🔬 Дополнительная проверка перед записью: сравнение изоморфизма

Проверка на реальном железе — окончательный критерий, но есть способ **без записи** исключить
целый класс проблем.

**Идея**: надёжный патч NoGZ изменяет свою базу `tee_a` **по шаблону** — изменения сосредоточены
в точках патча, определённых в profile (getter/callback/pc_patch у ATF и т. д.), а остальные
различия даёт подпись. Поэтому берём **уже проверенный на железе патч** как эталон и сравниваем,
**изоморфны** ли множества «областей различий с собственными базами»:

```bash
python tools/verify-patch-diff.py \
  --base-a  backup/tee_a.img \
  --patch-a tee/tee_nogz_rk_5M.img \
  --base-b  backup/tee_a_NEWROM_a91f5de.img \
  --patch-b tee/tee_nogz_shuilanA15_5M.img
```

Фактический вывод этого проекта:

```
  Число областей совпадает : ✅ да  (175 vs 175)
  Сумма байт совпадает     : ✅ да  (2953488 vs 2953488)
  Последовательность длин  : ✅ да

  ✅ Вывод: проверяемый патч изоморфен эталонному — тот же конвейер, без отклонений.
```

**→ Оба патча вышли из одного процесса сборки без отклонений.**
Это **не заменяет проверку на железе**, но исключает класс проблем «сборка пошла не так /
смещения в profile посчитаны неверно».

## ⚠️ Никогда не держите патчи для разных баз в одном каталоге

Мы реально на это наступили: **из-за неверно понятого имени файла был записан патч от другой
базы** ✗ — тогда показалось, что «устройство висит на втором экране», но позже выяснилось, что
**скорее всего просто не хватило времени ожидания** (после записи патча каждая загрузка занимает
около 2 минут). **Но не пробуйте это специально** ✗ — правильно использовать нужную базу ✓

```
/data/local/tmp/tee_patched.img     <- патч от другой базы ✗ и при этом имя самое «похожее на нужное»
/data/local/tmp/tee_nogz_new.img    <- нужный патч для этого устройства ✓ с непонятным именем
```

**→ Правило: в имени файла патча должно быть написано, для какой базы он и можно ли его писать
на это устройство** ✓ например `FLASH_THIS_shuilan_patch_for_this_phone.img` /
`DO_NOT_FLASH_rk_patch_wrong_base.img` ✓

Скажем прямее: **не держите на одном устройстве патчи для нескольких баз одновременно** ✗.
Если всё же держите — положите рядом `TEE_README.txt` с указанием, какой безопасен.

## ⚠️ Главное правило: патч **привязан к базе `tee`** —— **но «с другой базой загрузиться нельзя» опровергнуто измерениями**

Патч NoGZ изменяет **логику передачи управления у члена `atf`** внутри раздела `tee`, поэтому
он действителен только для **«той базы `tee`, с которой он был собран»**.

### 🧪 Решающий эксперимент, 2026-10-07: **с другой базой загрузка проходит нормально** ✓

```
Устройство 1 (исходный tee_a = f8f286f1…, т.е. собственная база патча rk)
  -> записан патч shuilan (17ec8497…, база a91f5ded…)   <- действительно другая база
  -> вернулось в сеть через 136 секунд после перезагрузки
  -> далее 12/12 проверок за 3 минуты, постоянно онлайн (не цикл перезагрузок)
  -> система в норме, tee_b всё время не изменялся
```

**→ Значит «с другой базой обязательно сломается» — неверно** ✗,
и «патч с другой базой не может загрузиться» — тоже неверно ✗.

**Чем на самом деле было то давнее «зависание»**: **задержка в 1–2 минуты, которая случается при
каждой загрузке** ✗ (см. пункт 12 в [docs/05-gotchas.md](../docs/05-gotchas.md)) —— тогда мы не дождались,
вошли в fastboot и сами прервали загрузку, которая бы завершилась успешно ✗.

**→ Тем не менее рекомендуется патч под вашу базу** ✓ —— не потому что «иначе зависнет» ✗,
а потому что **с той же базой консервативнее и меньше переменных** ✓.

> 🔑 **Практический вывод**: **не паникуйте, если прошили не ту базу** ✓ —— сначала он постоит
> на втором экране 1–2 минуты; **дайте ему 3 минуты**, и он скорее всего поднимется сам ✓
> (хотя резервная копия никогда не лишняя).

**Границы, подтверждённые измерениями** (что влияет, а что нет):

| Раздел / условие | Ломает ли патч при изменении | Как проверить |
|---|---|---|
| **`tee`** | ✅ **ломает** | сравнить хеш `tee_a` |
| `lk` | ❌ не ломает | проверено: после замены патч работал как обычно |
| `gz` / `dtbo` / `boot` / `system` | ❌ не ломает | пережило крупное обновление Android 15 → 16 |
| Между устройствами (одна модель) | ⚠️ **зависит от `tee_b`** | одинаковый `tee_b` = одна партия прошивки = одна база |

> 🛑 **Самое частое заблуждение: «прошил патч другого устройства — и оно работает» ≠ «разные базы работают»** ✗
>
> Вывод «раз устройство 1 работает со своим патчем, значит патч устройства 1 заработает и на
> устройстве 2» ✗ — **неверен** ✓:
>
> | | Устройство 1 | Устройство 2 |
> |---|---|---|
> | База патча устройства 1 (`f1511dca…`) | `f8f286f1…` | `f8f286f1…` |
> | Свой `tee_a` до записи | **`f8f286f1…`** | **`a91f5ded…`** |
> | Вердикт | ✅ **одна база** (иначе и быть не должно) | ❌ **разные базы** (не проверено) |
>
> **Случай устройства 1 с начала до конца был записью на ту же базу** ✓ — он доказывает, что
> «**одна и та же база работает**» ✓, и **не может служить доказательством, что «разные базы работают»** ✗.
> Единственный действительно «разные базы» случай — устройство 2 ⚠️, и даже тот вывод ненадёжен
> (см. раздел про смешивание ниже).

**Самый надёжный способ самопроверки — посмотреть на нетронутый слот `tee_b`:**

```bash
adb shell su -c 'dd if=/dev/block/by-name/tee_b bs=4096 2>/dev/null | sha256sum'
```

- `tee_b` не менялся (= штатный) → база `tee` всё ещё из штатной партии → подходит патч для штатной базы ✓
- `tee_b` тоже изменился → база заменена → обязательна пересборка ✗

> **Обновление ROM / OTA тихо меняет `tee_a`** ⚠️ — в этом проекте одно устройство **после записи
> ROM сменило `tee_a` с `f8f286f1…` на `a91f5ded…`** (хотя в пакете ROM образа `tee` вообще не было —
> это сделало обновление прошивки при первой загрузке или `super.img`).
> **Поэтому: перед записью ROM сделайте бэкап `tee_a`, после записи сравните хеши, и если он
> изменился — пересоберите патч.**

**обязательно останавливает загрузку на втором экране**. Но этот вывод **опирался на один
неверно истолкованный тест** ✗ —

**после записи патча NoGZ каждая загрузка изначально занимает почти 2 минуты на втором экране**
(см. пункт 12 в [docs/05-gotchas.md](../docs/05-gotchas.md)). Тогда мы просто не дождались и
посчитали устройство кирпичом ✗

**→ Правильная формулировка: «работает ли патч от другой базы» сейчас следует считать
«НЕ ПРОВЕРЕНО»** ⚠️, а не «обязательно сломается».

### Но по-прежнему настоятельно рекомендуем патч под вашу базу ✓

Причина **не** в том, что «иначе зависнет» ✗, а в том, что патч от другой базы несёт **TEE OS
другой партии**. Даже если система загрузится, сервисы TEE — keymint, DRM, Secure Element —
могут **не совпасть по версии** с текущей прошивкой устройства ✗.

### Как отличить «нормальную медленность» от «настоящего сбоя» ✓

| Признак | Нормально ✓ | Настоящий сбой ✗ |
|---|---|---|
| Экран | висит на **втором** экране (logo2) | висит на **первом** экране или после чёрного экрана **сам уходит в fastboot** |
| adb | устройство **видно** в `adb devices` | не видно, либо уже режим fastboot |
| Время | через 1–3 минуты загрузится сам | более 5 минут без изменений |
| Действие | **ждать** ✓ | восстановить бэкап ✓ |

# Как записывать

## 0) Сначала бэкап (обязательно, не пропускать)

```bash
adb shell su -c 'dd if=/dev/block/by-name/tee_a of=/data/local/tmp/tee_a_backup.img bs=4096'
adb shell su -c 'dd if=/dev/block/by-name/tee_b of=/data/local/tmp/tee_b_backup.img bs=4096'
adb pull /data/local/tmp/tee_a_backup.img
adb pull /data/local/tmp/tee_b_backup.img

# Запишите хеши — понадобятся для сверки при откате
sha256sum tee_a_backup.img tee_b_backup.img
```

## 1) Запись

```bash
adb push tee_nogz_rk_5M.img /data/local/tmp/tee_patched.img

# Сначала проверьте на телефоне, что скопированный файл не повреждён (важно!)
adb shell su -c 'sha256sum /data/local/tmp/tee_patched.img'
# должен совпасть с опубликованным sha256

adb shell su -c 'dd if=/data/local/tmp/tee_patched.img of=/dev/block/by-name/tee_a bs=4096 && sync'
```

## 2) Обратное чтение и проверка (обязательно)

```bash
adb shell su -c 'dd if=/dev/block/by-name/tee_a bs=4096 2>/dev/null | sha256sum'
# должен совпасть с опубликованным sha256
```

## 3) Перезагрузка и проверка KVM

```bash
adb reboot
# дождитесь завершения загрузки (первая занимает около 2 минут)
adb shell su -c 'ls -l /dev/kvm'
adb shell su -c 'grep -i kvm /proc/misc'
adb shell su -c 'dmesg | grep -i -E "sbc|kvm" | tail -20'
```

Ожидаемый вывод:

```
crw-rw-rw- 1 root root 10, 232 … /dev/kvm
232 kvm
[SBC] image atf header auth pass
```

## 🔙 Откат (как спасать, если завис на втором экране)

**Симптом**: после записи устройство останавливается на втором экране загрузки (логотип
крутится, затем чёрный экран или цикл перезагрузок), но устройство **всё ещё входит в fastboot**
(Громкость вниз + Питание).

```bash
# после входа в режим fastboot
fastboot devices
fastboot flash tee_a tee_a_backup.img
fastboot reboot
```

**Этот путь проверен на практике** — именно так в этом проекте спасли вторую базу.
**Затрагивается только `tee_a`**; остальные данные (пользовательские данные / система) целы.

> Запасной вариант 2: у устройства есть **слот B**, а `tee_b` никогда не изменялся — это естественная
> вторая копия.

# Об этих файлах

- Это **полные образы раздела `tee`, подписанные официальным инструментарием** (включая ATF,
  TEE OS и цепочку сертификатов MediaTek).
- Собраны с помощью [`mtk-mod-tee-nogz`](https://github.com/MT6895-Mainline/mtk-mod-tee-nogz) +
  [`pwnage24mtk`](https://github.com/kasnria001/pwnage24mtk). Определения смещений — в
  [`profiles/`](../profiles/), инструменты реверса — в [`tools/`](../tools/).
- В апстриме `mtk-mod-tee-nogz` явно сказано, что он **не содержит прошивок и
  предсобранных образов**; готовые образы лежат здесь для **сверки и переиспользования**.
  Решайте сами, подходят ли они вашей ситуации.
- **Прошивка связана с риском.** Используйте только на **принадлежащем вам оборудовании**
  и **сначала делайте бэкап**.
